Kaizen · Software Factory · A field study

The factory that debugged itself

Relay is a software factory — an autonomous line where AI executors move a card from spec to plan to implementation, through review and smoke and acceptance gates, to a merged pull request. Over twelve days we ran the line on its own source code. It surfaced its own defects, the quality gates stopped the line on each one, and every stop became an improvement. This is that improvement log — real cards, real commits, in the order they happened.

The improvement kata

One loop, run over and over

Kaizen isn't heroics — it's a loop you turn until it's boring. The factory floor already speaks this language: jidoka (a machine that stops itself the instant it makes a bad part), the andon cord (stop the line, pull a human), gemba (the actual place the work happens). Relay's gates are jidoka; a parked card is the andon. The catch is where most software teams leak value — the last edge:

Warm-up · hardening the line itself
Jul 22–23RE237 Half-built dark mode, live→Force light, hide the toggle detail

◆ Problem

The theme toggle exposed an unfinished dark mode that rendered broken.

✓ Countermeasure

Force light mode and hide the control — poka-yoke: remove the way to reach the bad state — then card the real removal.

Root cause

An incomplete feature was reachable in production before it was ready.

09ba22f · comment out darkmode
Jul 23precommit Flaky gate, shared lock→Hermetic per-run isolation detail

◆ Problem

Executor-lock tests fought live executors for one real lock directory, so the suite went red at random.

✓ Countermeasure

Hermetic test isolation — each run gets a private lock dir. A gate you can't trust can't stop the line.

Root cause

Tests shared mutable global state (the singleton lock) with running processes.

3b8a2bf · fix isolation
Jul 28–31RE239 · 240 · 244 Docs sprawl, no home rule→One home; doctor enforces it detail

◆ Problem

Docs duplicated and drifted; relay.md had bloated; nothing said where a given fact belonged.

✓ Countermeasure

Standardize: ADR 0008 defines nine homes — one fact, one home — and a relay-doctor check that fails the build on flow/factory drift.

Root cause

No single source of truth meant two copies of a fact could silently disagree.

#192 → #195 → #197 · taxonomy + doctor alignment checks
Dogfooding · the factory finds its own bugs
Aug 1TH8 → #199 Card drawer crash-loops prod→Render coerces any shape detail

◆ Problem

Opening one card drawer threw Protocol.UndefinedError and reload-looped the browser — a live outage.

✓ Countermeasure

The render now coerces any shape of change and never crashes — proven with a failing test first (TDD), then deployed.

Root cause

The drawer assumed one shape for an AI's change record; real data came back as a map.

5593883 · handle crashloop for ai changes
Aug 1–2RE249–254 Dogfooding surfaces six flow bugs→Filed, sequenced, pulled detail

◆ Problem

Running real work through the line exposed six ways the flow engine itself mishandled a card.

✓ The andon

Each was filed as a relay-bug card and sequenced at the top of the board — pull the cord, make the defects visible, work them in order.

Note

The next five entries are these cards, resolved one at a time on Aug 2.

↓ RE254 · RE253 · RE251 · RE249 · RE252 (and RE250, the deepest, still queued)
Aug 2RE254 Merge node races CI→Merge --auto, squash fallback detail

◆ Problem

The flow tried to merge before required checks were green, so the merge just failed.

✓ Countermeasure

Merge with --auto (let the platform merge once checks pass) and fall back to a direct squash.

Root cause

The step modeled merging as instantaneous instead of gated on CI.

d9042cc · merge node uses gh pr merge --auto
Aug 2RE253 Parked question, no reply→park_kind makes it answerable detail

◆ Problem

An engine-raised needs_input park rendered with no way to reply — the andon pulled, but the cord had no handle.

✓ Countermeasure

park_kind classifies A1 questions vs A4 escalations; the drawer makes an engine-raised park answerable.

Root cause

The UI only knew how to answer human-authored questions, not engine-raised ones.

e243772 · engine-raised needs_input parks are answerable
Aug 2RE251 Retry silently does nothing→Loop-back carries the findings detail

◆ Problem

When review sent a task back, the retry sometimes produced no commits — the fix request never reached the worker.

✓ Countermeasure

Every loop-back prompt now carries the reviewer's actual findings, not just the guard's generic message (executor v27).

Root cause

The retry dropped the payload that told the worker what to change.

4c0e31a · loop-back nodes receive the reviewer's findings
Aug 2RE249 Health check too shallow→relay audit: history + CI detail

◆ Problem

relay-doctor only checked name resolution — it couldn't see a broken run history.

✓ Countermeasure

A new relay audit — endpoint + CLI + doctor board-health — checks run history and CI parity. Sharpen the instrument that finds defects.

Root cause

Monitoring measured configuration, not the behavior that actually broke.

9d85a40 · relay audit with CI parity + board-health
Aug 2RE252 Failed review advances the batch→Failure holds the loop detail

◆ Problem

A failed quality_review advanced the foreach loop to the next task instead of stopping — a bad part rolled downstream.

✓ Countermeasure

A failing review holds the loop. This is jidoka in one line: don't pass defects to the next station.

Root cause

The loop advanced on completion, not on success.

#201 · failed quality_review no longer advances the foreach
The recurrence · the fix that fixes fixing
Aug 2–3RE185 · systemic Merged fixes never ran→Executors self-update to the line detail

◆ The real problem

Cards kept no-op'ing even after the fix was on main. The line was running executor v24 — four versions of fixes behind. "Merged" had never meant "running."

✓ The systemic fix

Executors now self-update: verified download, atomic install, and a restart at a safe job boundary. The countermeasure reaches the gemba on its own.

Root cause

The deepest waste wasn't any single bug — it was improvement latency: the gap between a fix landing in the repo and running on the line.

c919e00 · executors self-update — download + verified install + restart
Aug 3RE185 · follow-up Self-updater miscounts its guard→The gate caught it detail

◆ Problem

A benign "nothing newer" check burned the anti-thrash budget, and failed updates weren't counted correctly.

✓ Countermeasure

Fixed so a no-op update never counts against the cap. Notably, the whole-branch review gate caught this — jidoka on the machine that delivers jidoka.

Root cause

The safety valve counted the wrong events.

e494502 · 7cd44c4 · a benign "nothing newer" never counts toward the cap

The lesson worth teaching

The waste that mattered wasn't a bug

The gates caught every defect. But value only lands when the countermeasure reaches the line — and that was the gap.

Count the defects and it looks like a normal bug-fix week. Read the order and a different story shows up: the line's jidoka gates worked — every bad part was caught, every card parked, every root cause found. The improvement that mattered most wasn't in that list. It was the realization that a merged fix sitting in the repo is inventory, not value — the classic muda of work-in-progress that never ships. Self-update collapsed the distance from "merged" to "running" to zero.

That's the kaizen move a software factory makes that a person rarely does: don't just fix the defect — fix the mechanism that delivers fixes. Improve the system that produces the work.
