The factory that debugged itself

A software factory is an assembly line for building software: work flows from spec to plan to code, through automated review and testing gates, to shipped software — with AI agents doing much of the labor. For twelve days we pointed one such line at its own source code and let it help build itself. It surfaced its own defects, the quality gates stopped the line on each one, and every stop became an improvement. This is that log — real problems, real fixes, in order.

The improvement kata

One loop, run over and over

Kaizen isn't heroics — it's a loop you turn until it's boring. The factory floor already gives us the words for it: jidoka (a machine that stops itself the instant it makes a bad part), the andon cord (stop the line, pull a human), and gemba (the actual place where the work happens). Here the automated checks are jidoka, and a paused task is the andon. The catch is the last edge — where most teams quietly leak value:

The last edge — self-update — is the one this log is really about

Warm-up · hardening the line itself
Jul 23 The quality gate was flaky→Made every run isolated detail

◆ Problem

The automated tests competed with live jobs for one shared resource, so the build went red at random.

✓ Fix

Each run now gets its own isolated workspace. A gate you can't trust can't stop the line.

Root cause

Tests shared changeable global state with running processes.

3b8a2bf · isolate each test run
Jul 28–31 Docs drifted, no home rule→One home per fact, enforced detail

◆ Problem

Documentation duplicated and drifted, and nothing said where a given fact was supposed to live.

✓ Fix

Standardize: give every fact one home, and add a check that fails the build when copies drift apart.

Root cause

With no single source of truth, two copies of a fact could silently disagree.

#192 → #195 → #197 · one-home docs + a drift check
Running it on itself · the line finds its own bugs
Aug 1 A page crash-looped in production→Screen tolerates any data detail

◆ Problem

Opening one item threw an error that reload-looped the browser — a live outage for anyone who hit it.

✓ Fix

The screen now handles any shape of data and never crashes — proven with a failing test first, then deployed.

Root cause

The code assumed one data shape; real data came back in another.

◆ Problem

Putting real work through the line exposed six ways the system itself mishandled a job.

✓ The andon

Each became a visible defect at the top of the queue — pull the cord, make the problems visible, fix them one at a time.

Aug 2 Auto-merge raced the tests→Wait for checks, then merge detail

◆ Problem

The line tried to merge before the required tests were green, so the merge simply failed.

✓ Fix

Let the platform merge automatically once the tests pass, with a manual merge as a fallback.

Root cause

The step treated merging as instant instead of waiting on the tests.

card RE254 d9042cc · merge only after checks pass
Aug 2 It asked, but couldn't be answered→Made the question answerable detail

◆ Problem

When the system needed a human decision it paused and asked — but the screen gave no way to reply.

✓ Fix

Tell apart the kinds of questions the system can raise, and let a human answer them right there.

Root cause

The interface could only handle human-written questions, not ones the system raised itself.

card RE253 e243772 · answerable pauses
Aug 2 Retries silently did nothing→Retry now carries the feedback detail

◆ Problem

When a reviewer sent work back, the retry sometimes produced nothing — the feedback never reached the worker.

✓ Fix

Every retry now includes the reviewer's actual feedback, not just a generic "try again."

Root cause

The retry dropped the message that said what to change.

card RE251 4c0e31a · retries carry the feedback
Aug 2 The health check was too shallow→Made it check real behavior detail

◆ Problem

The health check only confirmed that names lined up — it couldn't see that jobs were actually failing.

✓ Fix

A deeper audit now checks real run history and whether local and CI results agree. Sharpen the instrument that finds defects.

Root cause

Monitoring measured configuration, not the behavior that actually broke.

card RE249 9d85a40 · deeper health audit
Aug 2 A failed check moved on anyway→A failure now stops the line detail

◆ Problem

A failed automated review let the batch roll on to the next item instead of stopping — a defect moved downstream.

✓ Fix

A failing review now holds the line. Don't pass a defect to the next station.

Root cause

The loop advanced when a step finished, not when it succeeded.

card RE252 #201 · a failed review stops the batch
The recurrence · the fix that fixes fixing
Aug 2–3 Merged fixes weren't running→The line updates itself detail

◆ The real problem

Jobs kept failing even after the fix was merged. The machines on the floor were running a version four fixes old. "Merged" had never meant "running."

✓ The systemic fix

The machines now update themselves: verified download, safe install, and a restart between jobs. The fix reaches the floor on its own — this is the last edge of the loop above.

Root cause

The deepest waste wasn't any single bug — it was improvement latency: the gap between a fix landing in the repo and actually running.

card RE185 c919e00 · the line updates itself
Aug 3 The updater's own guard misfired→A review gate caught it detail

◆ Problem

A safety limit inside the self-updater miscounted, treating a harmless "nothing new" as a failed attempt.

✓ Fix

Now a no-op update never counts against the limit. Notably, an automated review caught this — quality control on the machine that delivers quality control.

Root cause

The safety valve counted the wrong events.

card RE185 e494502 · 7cd44c4 · don't penalize a no-op update

The lesson worth teaching

The waste that mattered wasn't a bug

The gates caught every defect. But value only lands when the fix reaches the line — and that was the gap.

Count the defects and it looks like a normal bug-fix week. Read the order and a different story shows up: the line's jidoka checks worked — every bad part was caught, every job paused, every root cause found. The improvement that mattered most wasn't in that list. It was noticing that a merged fix sitting in the repo is inventory, not value — the classic muda (waste) of work that's finished but never shipped. Self-update collapsed the distance from "merged" to "running" to zero.

That's the move a software factory can make that a person rarely does: don't just fix the defect — fix the mechanism that delivers fixes. Improve the system that produces the work.

  • jidokaStop the line on a defect instead of passing it downstream — the "a failure stops the batch" fix is exactly this.
  • andonA paused job pulls in a human and makes the problem visible — but the cord needs a handle you can actually pull.
  • poka-yokeRemove the path to the bad state instead of warning about it — make the screen tolerate any data so it can't crash.
  • gembaImprovements have to reach where the work actually happens — the running machine, not the repository.
  • standardizeTurn every fix into a permanent check — one home per fact, a deeper health audit — so the same defect can't return.
