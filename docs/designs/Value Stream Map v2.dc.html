FAN-OUT · COMING

Two kinds, one treatment — and what each buys

The engine already has a :parallel node type (Schemas.Flow.Node.types/0); it is deliberately excluded from runnable_types/0 and the Code flow does not use it yet. So the map ships fan-out as a topology toggle, not a claim: flip the prop and the same per-visit times re-solve as a fork/join, collapsing three slots into one. The delta is computed, not asserted.

FANNING final_review ∥ smoke ∥ acceptance RETURNS {{ fanGain }}

Today those three run strictly in series, so every minute of all three is on the critical path; fanned, only the slowest branch is — {{ fanDetail }} The trap: one shared final_fix rewinds to precommit, so a fan re-serialises the moment any branch fails. Fan-out only pays once each branch owns its fix — the same argument ADR 0011 makes for a parameterised verify subgraph. And against the card clock it is worth {{ fanCardPct }}, which is the honest way to rank it.

WIRING IT UP

What has to be written

Both levels are derivable today — nothing new has to be tracked. Level 2 rolls up from Runs.node_metrics_for_flow/2, which already has duration, cost, attempts_mean, loop_laps and a verdict split per node. Level 1 folds Schemas.Activity rows into per-state spans: :moved carries from_stage/to_stage, :approved/:rejected carry the gate decisions, :needs_input/:input_answered bracket a park — and the pruner ages out runner chatter only, never an audit row, so the card's story is durable. Whatever lands must agree with the shipped Flow Metrics page rather than restate it.
